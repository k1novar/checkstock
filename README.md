# CheckStock

Веб-прототип для тестового задания «Где сейчас товар?». Python 3.12, FastAPI, PostgreSQL 17, SQLAlchemy 2; интерфейс на HTML/CSS/JavaScript без сборщика и CDN. Один магазин, три тестовых артикула, два ФФ. Интерфейс и сообщения на русском.

## Быстрый запуск

Нужны Docker Engine / Docker Desktop и Docker Compose v2, свободный порт 8000, доступ к Docker Hub и PyPI при первой сборке.

```bash
docker compose up --build -d
```

Откройте **http://localhost:8000**. Swagger: **http://localhost:8000/docs**. Проверка доступности: **http://localhost:8000/health**.

```bash
docker compose logs -f app
docker compose down
```

Перезапуск сохраняет данные в `pgdata`. Демонстрационные приходы создаются только при первом заполнении базы. Чтобы намеренно удалить демонстрационную базу и начать заново:

```bash
docker compose down -v
docker compose up --build -d
```

Приложение слушает только localhost хоста. Пароли в Compose — исключительно для локального тестового стенда. Сборка и запуск проверены в среде подготовки: см. `docs/VERIFICATION.md`.

## Что проверить за пять минут

Начальная таблица:

| Артикул | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

1. «Новая операция» → резерв FBS → SKU-101 → Север → 3 → заказ `FBS-001`. На Севере: физически 10, резерв 3, доступно 7.
2. Попробуйте перемещение 8 единиц с Севера на Юг. Получите отказ, хотя суммарно доступно 13. В ошибке показана доступность по ФФ. Никакие остатки и события не меняются.
3. Переместите 4 единицы с Севера на Юг. До приёмки: Север 6, Юг 6, между ФФ 4. В «Отправки и резервы» нажмите «Принять»: Север 6, Юг 10, между ФФ 0.
4. Отправьте 2 единицы FBO с Юга на `WB · Коледино`: Юг 8, FBO в пути 2.
5. Отправьте резерв FBS из шага 1: Север 3, резерв 0, FBS в пути 3. Повтор запроса не спишет товар ещё раз.
6. Примите FBO: на маркетплейсе 2, FBO в пути 0.
7. Во вкладке «Склады» удалите Север в архив. Его 3 единицы остаются видны; новые резервы запрещены, доступен вывоз остатка.
8. Итог SKU-101: 3 на Севере + 8 на Юге + 2 на маркетплейсе + 3 у перевозчика FBS = исходные 16. История содержит каждое изменение.

Отмена резерва доступна до отправки; она освобождает доступный остаток, не меняя физическое количество. Для FBS дополнительно есть подтверждение доставки, чтобы товар не оставался в пути навсегда.

## Автотесты

Тесты запускаются в изолированном окружении через Docker. Локальная установка PostgreSQL или Python не требуется. Рабочие данные не затрагиваются.

```bash
docker compose --profile test run --build --rm tests
```

Выполнение всех 30 тестовых случаев подтверждено (включая 4 конкурентных теста на PostgreSQL). При любом падении не считать сдачу проверенной.

## Ключевые решения

**Остаток и резерв — разные величины.** `available = physical - reserved`. Резерв остаётся физически на ФФ; при отправке FBS одновременно уменьшаются физическое количество и резерв. Перемещение и FBO списывают физическое количество в момент отправки. Товар в пути хранится в операции, а не дублируется на двух складах.

**FBO после приёмки не исчезает.** Принятые поставки входят в отдельный остаток маркетплейса. Он вычисляется по завершённым FBO-операциям. В этой версии нет продаж с маркетплейса или возвратов. Пункты назначения FBO — подписи; детализация есть в операциях, в сводке итог по всем маркетплейсам.

**Удаление ФФ означает архивирование.** Внешние ключи, остатки и история остаются. Запрещены новые приходы, резервы и FBO с архивного ФФ; разрешены вывоз доступного товара на действующий ФФ и завершение уже начатых операций. Даже если ФФ назначения архивирован после отправки, уже едущий товар можно принять: фактический приход нельзя потерять. Он будет виден на архивном ФФ, после чего его можно вывезти.

**Нехватка проверяется на выбранном ФФ.** Общий остаток не даёт права списывать товар с другого склада. API возвращает 409 и доступность по каждому ФФ. Менеджер сам выбирает другой ФФ или перемещение; скрытого перераспределения нет.

**Запись атомарна.** Изменение счётчиков, переход операции, событие журнала и сохранение ключа запроса выполняются одной транзакцией. Ошибка откатывает всё. Ограничения БД запрещают отрицательный остаток и резерв сверх физического количества.

**Конкуренция решена просто для одного магазина.** Перед каждой командой берётся `SELECT ... FOR UPDATE` на строку магазина. Запросы разных процессов/воркеров сериализуются в PostgreSQL, поэтому нельзя одновременно зарезервировать одни и те же единицы. Чтение сводки берёт тот же замок и возвращает согласованный срез. Это осознанный компромисс однодневного прототипа: меньше пропускная способность, но понятная корректность. При росте нагрузки — блокировки пар `(warehouse_id, product_id)` в стабильном порядке, отдельный срез чтения и нагрузочные тесты. Для ожидающего замка нет отдельного таймаута в этой версии: не держим внешние вызовы внутри транзакции.

**Два уровня защиты от повторов.** UUID `request_id` уникален в БД; тот же ключ и те же данные возвращают прежний ответ, другие данные с тем же ключом дают 409. Дополнительно повтор подтверждения уже завершённого перехода с новым UUID — безопасная операция без новых движений и событий. Отмена после отправки запрещена. Интерфейс сохраняет незавершённый запрос в localStorage и повторяет его с прежним ключом после потери ответа/перезагрузки. Это прототип для одного локального оператора; координация pending-запроса между несколькими вкладками не реализована.

**Журнал помогает сверять учёт.** Событие хранит артикул, количество, исходную/целевую подпись, ID операции и дельты физического остатка/резерва по ФФ. Названия являются снимком на момент события: переименование склада не переписывает прошлое. API не предоставляет изменение/удаление событий; защита от прямого изменения БД не реализована. Основной учёт — транзакционные счётчики и операции, а не полноценный event sourcing.

**Баланс по артикулу:**

```text
Все приходы = физически на всех ФФ (включая архив)
            + в пути ФФ + в пути FBO + в пути FBS
            + принято на маркетплейс + доставлено клиентам
```

Резерв уже содержится в физическом остатке и второй раз не суммируется. Тест дополнительно восстанавливает счётчики из дельт журнала после 70 воспроизводимых случайных действий.

## API

- `GET /api/state` — единый согласованный срез товаров, складов, операций и истории.
- `POST /api/commands` — команда с обязательными `request_id` и `action`.
- `GET /health` — доступность API и соединения с БД.

Пример прихода, повторите тот же запрос для проверки идемпотентности:

```bash
curl -X POST http://localhost:8000/api/commands \
  -H 'Content-Type: application/json' \
  -d '{"request_id":"01e8b246-06f1-48ad-9078-aeaa8c084960","action":"receipt","product_id":1,"warehouse_id":1,"quantity":2}'
```

| action | Поля помимо request_id |
|---|---|
| warehouse_create | name |
| warehouse_rename | warehouse_id, name |
| warehouse_archive | warehouse_id |
| receipt | product_id, warehouse_id, quantity |
| reserve | product_id, warehouse_id, quantity, destination (заказ) |
| transfer | product_id, warehouse_id, target_id, quantity |
| fbo | product_id, warehouse_id, quantity, destination (склад МП) |
| ship / cancel / receive / deliver | operation_id |

Ошибки: 422 — форма/количество, 404 — неизвестный объект, 409 — недостаток/конфликт состояния/ключа, 503 — временная ошибка БД. `quantity` — строго целое число от 1 до 1 000 000. Каждая операция содержит один артикул и принимается целиком; частичные поставки и пакетные документы не входят в объём задания. Разные UUID означают разные команды создания: два новых резерва с одинаковым номером заказа разрешены; для интеграции понадобится уникальный внешний ID заказа/строки.

## Границы и сдача

Это локальный прототип без аутентификации, ролей, интеграции WB, возвратов, списаний, партий и пагинации. До внешнего доступа нужны авторизация, HTTPS, секреты, резервное копирование и проверка восстановления, миграции, контроль доступа к БД и наблюдаемость. Сейчас на экран загружается вся история — для тестовых объёмов это упрощает проверку.

Подготовлено с помощью ИИ: код, интерфейс, тесты и документация. Пройденные проверки и ограничения зафиксированы отдельно.

Для сдачи: проект размещён в Git-репозитории, видео записано. PostgreSQL-тесты и запуск выполнены.
